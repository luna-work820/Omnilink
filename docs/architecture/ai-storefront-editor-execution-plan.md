# Omnilink AI 店铺网页设计：插件式执行方案

日期：2026-10-16。本文同时记录实施方案和阶段进展。

## 当前进展（2026-10-16）

- 阶段 0 已接入 `@puckeditor/core@0.23.0`；「网页设计」现在直接打开 Puck 编辑器，旧版编辑器和重复风格入口已从运行时代码移除。
- 已建立 `StorefrontSchema ↔ Puck Data` 转换和往返测试，保留区块 ID、顺序、可见性、正文、样式、设置、全局资料和主题；修复 Schema 归一化丢弃语言、字体和自定义 token 的问题。
- Puck 画布复用公开店铺的 `DynamicSectionRenderer`，并接入现有四套风格的 Puck 插件；演示店铺预览读取与公开页一致的演示商品。
- 已在浏览器验证区块点选、标题即时预览及风格插件入口。TypeScript、定向 ESLint、往返测试及 `next build --webpack` 通过。
- 真实商家草稿保存与发布、资源目录、AI 插件、版式母版和多页面仍按下述阶段推进；演示店铺本身不允许持久化。

## 目标与选型

商家先从知识库选择已确认知识、品牌资产、视觉风格和素材，组成一次设计所用的固定元素；再基于经过人工设计的商业页面母版，让 AI 生成首页、商品集合页和商品详情页。之后可点选区块对话修改、手工拖拽编辑、预览草稿并发布。现有商品、购物车、结账、权限和版本发布流程继续由 Omnilink 负责。

- **编辑底座**：安装 [Puck core](https://github.com/puckeditor/puck)（MIT），通过它的 [Plugin API](https://puckeditor.com/docs/extending-puck/plugins)接入 Omnilink 的「AI 修改」「视觉风格」「商品选择」面板。Puck 的配置决定可用组件及字段，不允许自由执行 AI 输出的代码。
- **生成机制**：借鉴并按 MIT 许可要求移植 [OpenPage](https://github.com/buildingopen/openpage) 的「区块类型 + 版式 variant + 主题 + JSON 输出」模式，改成 Omnilink 的商业区块和数据契约。OpenPage 是独立应用，不作为整站运行时嵌入。
- **AI 服务**：自建 Omnilink API 连接现有模型服务。Puck 官方 AI 服务单独计费；首版不依赖 Puck Cloud，积分仍由 Omnilink 统一核算。[Puck 定价](https://puckeditor.com/pricing)
- **唯一数据源**：已发布及草稿均使用 Omnilink 的 `StorefrontSchema`，Puck 的 `Data` 只作为编辑器内的视图格式。新增双向转换器，禁止再增加一份独立的可发布页面数据。

## 新增一层：知识库设计资源层

知识库是商家选择设计依据的统一入口，底层仍保留各自的数据所有权；不把不同资源硬塞进同一张“知识”表。资源按四类展示：

| 类型 | 内容与现有来源 | 设计时的规则 |
| --- | --- | --- |
| 知识 | 已确认的品牌定位、商品事实、目标人群、服务承诺；来源可追溯。 | 用于生成文案与选区块；草稿、推断和待审核主张只能作提示，不能直接作为对外事实。 |
| 资产 | Logo、品牌标识、商品主图、已批准的品牌资料；可接现有 `brand_assets`、`catalog_media`。 | 可选择「必须使用」，保存稳定 ID；渲染时读取授权资源，不让 AI 改造 Logo 或捏造商品图。 |
| 风格 | 现有四套视觉主题，以及商家确认的品牌色、字体、按钮和排版偏好。 | 作为全站约束；AI 在允许的 token 和组件 variant 内组合，不能覆盖已锁定的品牌规则。 |
| 素材 | 活动图、视频、场景图、参考图和 moodboard 等可用于版面的媒体。 | 标记版权/使用范围、比例、用途与审核状态；“参考”素材只影响构图方向，“指定使用”素材绑定到页面。 |

### 选择与使用方式

在知识库增加「用于网页设计」选择模式。商家可以跨四类勾选少量元素，选定页面目标并点击「用所选元素设计网页」。网页编辑器中的资源插件也能打开同一个选择器。每项选择有三种明确意图：**必须使用**、**作为参考**、**不要使用**。商家还可以锁定 Logo、主色、指定商品及主图，后续 AI 对话修改不得替换这些元素；要解锁须由商家操作。

一次生成形成一个 `DesignContext`（设计上下文包）：保存 store/organization、所选资源 ID 与版本、用途意图、锁定状态、目标页面、选择时间；仅把需要的事实摘要与素材元数据送入模型。页面 Schema 记录实际使用的资源 ID 和来源版本，编辑器提供「本页使用了哪些知识/资产/素材」回看。对可能变化的价格、库存等动态字段只保存商品 ID 并实时读取，不快照成静态文案。

资源目录的接口负责按店铺权限、审核状态、客户可见性和使用权过滤。私有文件不能因为进入设计上下文就变成公开 URL；发布前再次检查素材可访问性、商品归属和资源授权。资源被撤回或失效时，已发布页按资源类型显示安全的替代状态，并提示商家修复。数据库持久化与 RLS 作为该层的前置工作，具体表结构在实施阶段结合现有 `catalog_media`、`brand_assets` 和知识来源模型设计，避免重复存储原始文件。

## 插件边界

```
知识库选择器 ──> DesignContext ────────┐
视觉风格库(themeId/tokens) ────────────┼──> StorefrontSchema ──> 共享渲染器 ──> 草稿/发布
商业母版(archetype/variants) ──────────┘             ↑
                                                  Puck 编辑器
                                       ┌──────────┼──────────┐
                                   资源插件     风格插件     AI 插件
```

1. **风格插件**：选择四套现有主题；展示字体、颜色、圆角等允许调整的 token，保存为 schema.theme。风格切换不替换商家文案和商品绑定。
2. **资源插件**：复用知识库选择器，显示已选知识、资产、素材及锁定状态；Puck 自定义字段提供商品/集合和媒体选择，保存稳定 ID。渲染时读取当前店铺真实数据，无商品显示空态，不伪造商品和价格。[Puck 外部数据字段说明](https://puckeditor.com/docs/integrating-puck/external-data-sources)
3. **AI 插件**：在 Puck 左侧插件栏提供「用所选元素生成整页」「修改选中区块」「修改全页」三种操作；调用 Omnilink 服务端。返回结构化候选变更，在画布预览，用户确认后才写入编辑状态。每次操作记录可撤销历史和用量，并保留资源引用。
4. **Puck core 内置能力**：使用区块抽屉、字段面板、页面大纲和画布；不重复开发拖拽器。[Puck Plugin API](https://puckeditor.com/docs/extending-puck/plugins)

## 页面母版与区块设计

先由设计师完成三套真正不同的商业母版，而非同一顺序换配色：

| 母版 | 首页节奏 | 适合品类 |
| --- | --- | --- |
| 品牌叙事 | 大幅视觉 → 品牌理念 → 精选商品 → 工艺/故事 → CTA | 设计、家居、精品品牌 |
| 商品目录 | 分类导航 → 商品集合 → 筛选/利益点 → 品牌信息 | 多 SKU、明确搜索需求 |
| 活动转化 | 活动主视觉 → 主推商品 → 优惠说明 → 信任信息 → CTA | 新品、季节活动 |

每个商业区块提供 2–4 种人工设计的版式，例如 hero 的居中/左右分栏/全幅图，商品区的网格/横向精选，品牌故事的图文左右/编辑式长文。版式应定义桌面和手机布局、图片比例、文字长度范围、空数据状态、键盘可达性，并满足项目同排元素等高和垂直居中规则。首页、集合页、详情页共享品牌级颜色、字体、按钮、间距和导航规则；购物车/结账只开放安全的视觉 token。

建议先在现有 `StorefrontSchema.sections` 上增加可选的 `section.variant`、`section.binding` 和 `archetypeId`。根级 `sections` 保持为首页，以兼容现有 `save_storefront_version` RPC、旧店铺与公开首页。多页面阶段再增加可选的 `pages.collection`、`pages.product`；旧版 schema 在读取时适配，历史发布记录保持可读。所有可选值由静态注册表和校验器限定，不接受 AI 生成的任意 HTML、脚本或 CSS。

## AI 生成与修改流程

1. **收集上下文**：读取商家选定的 `DesignContext`，包含已确认知识、指定或参考的资产/素材、锁定规则、风格 ID、真实商品/集合的 ID 与必要摘要、目标页面和用户指令。联系方式和评价只来自商家已保存且允许对外使用的资料；缺失时隐藏对应内容。未选择的私有知识不进入模型上下文。
2. **先出页面计划**：AI 选择母版、区块顺序、variant、资源 ID 绑定和文案。服务端只接受结构化 JSON，并校验区块白名单、ID 归属、链接、图片与素材授权、长度、锁定规则和必需商业入口。
3. **生成候选草稿**：从已设计的区块组件渲染，不执行代码。展示桌面/手机预览和与现有草稿的变更摘要。
4. **对话修改**：用户选中区块后默认只把该区块、相邻上下文与品牌约束送给模型；模型返回有限的 patch 操作。全页重排由用户明确选择。旧 section ID 和未修改字段保持不变。
5. **确认与发布**：候选 patch 通过再次校验后进入可撤销的本地编辑状态；保存到 `storefront_versions` 草稿；发布沿用现有权限与版本 RPC。失败不改变已发布版本。

成本控制：默认使用现有已接通的轻量模型配置处理结构化生成和局部修改；复杂整页重设计再路由到能力更强的模型。记录每次调用的输入/输出 token、耗时和实际供应商成本，再映射 Omnilink 积分。对模型与价格不在设计文档中写死，发布前用真实商家样本评测视觉质量、JSON 有效率和单次成本。

## 实施顺序与验收

| 阶段 | 主要交付 | 完成条件 |
| --- | --- | --- |
| 0. 兼容性试点 | 在隔离入口安装 Puck；实现 `StorefrontSchema ↔ Puck Data` 转换和一两个真实区块，不动数据库。 | 旧店铺打开、编辑、保存、刷新后内容与风格不丢；预览与公开渲染一致。若转换无法可靠往返，停止替换编辑器，保留现有编辑器并只移植生成机制。 |
| 1. 知识库资源层 | 服务端资源目录、状态/可见性/版权规则、跨类选择器、`DesignContext` 与资源引用；接通现有知识、品牌和商品媒体来源。 | 跨设备可读取同一选择结果；私有或未确认内容不会被发布；指定素材可按 ID 回看和追溯。 |
| 2. 设计系统 | 三套母版、核心区块 variant、桌面/手机规范；接入现有四套风格。 | 同一母版在四套风格下结构稳定；三套母版的布局有明显差异，真实商品和指定素材可展示。 |
| 3. 编辑器插件 | Puck 画布、风格/资源插件、旧草稿导入、保存/发布接线。 | 可以选择固定元素、拖拽、修改、撤销、预览、保存草稿和发布；不影响旧店铺前台。 |
| 4. AI 生成插件 | 基于 `DesignContext` 的整页生成、选区修改、结构化校验、候选预览、用量记录。 | 生成内容无虚构商品/评价/联系方式；锁定元素保持不变；局部修改不改动其他区块；非法输出不能发布。 |
| 5. 多页面扩展 | 集合页和商品详情页的可控版式；旧 schema 迁移读取。 | 首页、集合、详情具有统一视觉，真实商品与购买动作正常；购物车和结账流程回归通过。 |
| 6. 灰度上线 | 对新建店铺或少量测试店铺开启，以版本恢复作为回退方式。 | 对比浏览器预览与实际发布页，收集生成成功率、编辑成功率、单次成本和发布错误率后扩大范围。 |

建议每阶段单独提交和验收。先做不写数据库的 Puck 兼容性试点，尽早排除底座风险；正式生成之前，再让知识库选定元素成为可持久化、可授权、可追溯的设计输入。这些通过后，再投入大规模母版设计和 AI 调用。

## 可以直接执行的工作清单

下面每一步单独形成可评审的变更。实施代码前先按仓库 `AGENTS.md` 阅读所涉及的 `node_modules/next/dist/docs/` 指南；涉及 Supabase 时核对当时文档、迁移与 RLS 规则。每一步开始前记录现有工作树状态，保留与本功能无关的未提交修改。

### 步骤 0：冻结数据边界并做 Puck 试点

1. 为现有 `StorefrontSchema`、四套主题、首页/商品/集合预览和草稿/发布各保存一份测试样本；包含中英文、空商品、旧版 theme、已有商家联系方式。
2. 安装并锁定 `@puckeditor/core` 版本及 lockfile；在独立试验入口加载 Puck，不替换现有 `StorefrontEditor`。
3. 在 `lib/storefront/` 建立 `toPuckData`、`fromPuckData` 纯转换；先映射 hero 与 featured_products，并保留稳定 section ID、顺序、可见性、content/style/settings、theme、globalInfo。
4. 使用 `DynamicSectionRenderer` 和同一主题令牌显示画布；检查 Puck iframe 内字体、链接和商品数据的预览效果。修正 `normalizeStorefrontSchema` 丢失的 theme 字段。
5. 对旧样本执行 `schema → Puck Data → schema` 往返测试，再实际编辑保存草稿、刷新、发布到测试店铺，比较前台页面。

**门槛**：旧字段不丢、商品引用不变、未修改的 sections 不变、预览与发布结果一致。任何一个做不到，先修转换层；不能无损映射时改用现有编辑器承接后续方案。

### 步骤 1：建立可供设计使用的知识库资源目录

1. 按 store/organization 梳理来源：`KnowledgeEntryRecord` 与本地文件、`brand_assets`、`catalog_media`、商品记录和 `lib/themes/registry.ts`。明确每项的所有者、审核状态、公开用途、来源版本和持久化位置。
2. 将商家确认的知识事实和来源记录持久化到服务端。浏览器 localStorage 文件只能作为导入来源；导入后由商家核对，不能自动成为已确认事实。`knowledge_uploads` 目前是隔离上传记录，不能当成已解析知识或可直接发布的媒体。
3. 建立只返回统一元数据的资源目录服务：`id`、`kind`、`origin`、`title`、`status`、`usageRights`、`preview`、`revision`、`storeId` 等；实际图片/文件仍留在原有存储系统。目录查询按店铺、组织、角色和状态过滤。
4. 为一次设计选择持久化 `DesignContext`：目标页面、所选资源引用及 `required`/`reference`/`excluded` 意图、锁定状态、版本号、创建/修改人。保存前与生成前都重新验证引用归属和可用状态。
5. 在知识库实现跨四类的「用于网页设计」选择器和已选清单；在编辑器资源插件复用。选择和取消必须跨刷新、跨设备保持一致。
6. 数据库变更用项目现有迁移流程，给新表设置 RLS 和按组织/店铺的授权谓词；验证不同店铺、不同角色对目录、选择结果、私有文件的读写边界。不要通过公开 URL 暴露原始私有文件。

**门槛**：商家从知识库指定 Logo、一个商品、一个已确认事实、一张有公开使用权的图，刷新后在编辑器中仍可选择；换店铺账号无法读到这些资源；未确认知识不能成为公开文案。

### 步骤 2：人工设计母版和区块版式

1. 先为三套母版画出首页的桌面与手机线框，列出每套必需区块、可选区块和阅读顺序；商品集合页、详情页补充对应版式规则。
2. 建立 `section type × variant` 注册表，写清允许的字段和绑定类型。首批实现 header、hero、featured_products、collection、image_text、cta、footer 的必要变体；testimonials/faq 仅在有已确认内容时显示。
3. 把版式实现放入共享渲染组件，消费现有 `--th-*` token；同排按钮和卡片等高并垂直居中。网页设计工作台的主要操作按钮沿用当前黑色主体，聚焦输入区沿用固定彩色渐变，不做流动动画。检查窄屏、长中文/英文、缺图、空商品、键盘焦点和缩放。
4. 改掉 AI 模板固定 10 区块校验，同时保留旧 10 区块页面的读取兼容。母版验证器只允许注册过的区块/variant/绑定，拒绝脚本、任意 CSS 与不安全链接。

**门槛**：三套母版不只是换颜色或文案；四套风格都能套用；页面结构在手机上仍完整；现有店铺页面不需要数据迁移就能继续显示。

### 步骤 3：正式接入编辑器和资源插件

1. 将 Puck 接到 `StorefrontHub` 的「视觉装修」入口；新旧编辑器通过店铺级开关切换，不同时写同一草稿。
2. 注册商业区块组件、字段分组、资源/商品选择字段和 Puck 插件栏；Puck 画布及公开页共用渲染逻辑。
3. 风格插件只改 theme token；资源插件只保存被选资源的 ID、用途和绑定，不复制商品价格或敏感文件内容。
4. Puck 的 Save/Publish 按钮分别调用现有 `saveStorefrontSchemaAction`、`publishStorefrontAction`；模板应用先生成草稿，商家确认后发布。离开页面提示未保存修改。

**门槛**：可拖拽、编辑、撤销、切风格、换素材、保存草稿和发布；公开页与编辑预览一致。

### 步骤 4：接入自有 AI 插件

1. 在服务端新增「生成页面计划」和「应用局部修改」接口；输入为用户指令、当前 schema 版本、已验证 `DesignContext` 和可用区块/variant 清单。接口先检查身份、店铺归属和积分/调用限额。
2. 模型只返回结构化候选：母版/区块/variant/文案/资源 ID 或受控 patch。服务端复核 JSON 结构、引用归属、素材权利、锁定项、当前版本以及商品购买链路；若编辑期间草稿版本已变化，拒绝旧版本 patch 并要求重新预览。
3. 首版只允许 `replaceText`、`setVariant`、`reorderSection`、`addSection`、`removeSection`、`bindResource` 等有限操作。默认只修改选中区块；全页改版显式触发。
4. 候选先展示变更摘要和桌面/手机预览，确认后进入可撤销编辑状态；不会自动保存或发布。记录模型、token、实际成本、失败原因和所引用的资源版本。
5. 用真实品类和四套风格构造评测样本，比较轻量模型与强模型的视觉质量、结构化成功率、响应时间和成本；完成评测后再决定默认模型和积分单价。

**门槛**：AI 不能引用未选私有知识、替换锁定资源、编造商品/评价/联系方式或修改结账流程；失败请求不改变草稿与线上版本。

### 步骤 5：多页面、发布与灰度

1. 保留根级 `sections` 为首页，逐步加入集合页和详情页配置；公开路由按已发布版本读取，旧版本仍由现有固定模板渲染。
2. 检查 `save_storefront_version` 的兼容约束；在需要记录来源时，将已有 `storefront_versions.source_snapshot`、`generation_brief`、`generation_model` 纳入保存路径，而不是另起一份发布记录。任何 RPC 签名改动先验证旧调用仍工作。
3. 发布前再次校验资源、商品可见性、链接、锁定规则和页面 Schema；保存的草稿与当前已发布指针分开。增加「恢复旧版本」操作：读取旧版 schema，新建一个草稿供预览，再由有发布权限的商家重新发布，不直接改写历史版本。灰度先面向测试店铺，再面向新建店铺。
4. 比对草稿预览、实际公开页和手机端，回归商品详情、购物车、结账、C 端入口；记录错误率、生成成功率、平均成本和手工修改次数。

**门槛**：旧店铺可用，关闭新编辑器开关即可回到旧入口；已发布版本不会被失败生成覆盖；商品与下单流程正常。

## 验证清单与交接标准

- **自动检查**：针对 schema 往返、旧版读取、variant 白名单、资源归属、锁定项、patch 作用域和发布校验写有意义的测试；每阶段运行 `npm run lint`、`npm test`、`npm run build`。数据库阶段执行本地迁移与 RLS 权限验证。
- **浏览器检查**：用一个真实测试店铺完成「知识库选 4 类资源 → 生成 → 局部修改 → 手工编辑 → 保存草稿 → 刷新 → 发布 → 公开页查看 → 恢复旧版本」；分别检查桌面和手机。
- **发布检查**：匿名用户只看到已发布内容；编辑角色能存草稿，只有项目现有权限允许的角色能发布；跨店铺资源不可读；私有素材不返回公开 URL。
- **交接材料**：记录锁定的 Puck 版本与 OpenPage 借鉴代码来源/许可、Schema 版本与迁移说明、插件接口、模型评测结果、积分换算规则、灰度开关与回退步骤。

## 主要风险及处理

- **Puck 数据与现有 schema 不同**：限定受支持字段，建立往返测试；Omnilink schema 始终为唯一持久化格式。
- **不同主题实际只换颜色**：母版和 variant 分层，设计验收要看整页布局与移动端，而不只看 token。
- **AI 乱改购买链路或编造资料**：模型只输出白名单 JSON/patch，真实商品通过 ID 绑定，付款/结账组件不开放任意结构编辑。
- **开源许可和服务费用**：Puck core 与 OpenPage 均为 MIT，复制源码时保留原许可及版权信息；Puck 官方 AI Cloud 为单独服务，首版使用自有 AI 插件与模型账单。
- **旧模板直接发布覆盖**：模板应用改为草稿预览确认，已有线上版本可以恢复；历史旧 schema 保留读取兼容。
- **知识库当前分散在内存、本地存储和多个数据库来源**：以服务端目录聚合，不直接让编辑器读取本地状态；新目录只存元数据、状态与引用，原始商品/媒体仍由各自系统维护。
- **素材权利和知识可信度**：只有商家授权且符合用途的素材能被绑定到公开页面；对外文案只使用已确认的知识事实，并保留来源。
