# 工作台开源项目评测缺项

## 评测范围

检查 `/dashboard` 首页及其直接连接的品牌、知识、来源、商品和发布工作流。开源项目用于比较能力模型，不复制其页面或代码。首页新增内容只作为欢迎区下方的折叠评测清单，不替换原欢迎动效、对话输入、历史侧栏或现有操作。

## 现有基础

- 首页已有 AI 对话、Skill、模型选择、商品和知识资料上下文、图片上传、语音输入、任务历史与全屏创作。
- 应用已有商品资产、品牌工作室、知识库、来源记录等入口。
- 数据库迁移已建立商品来源关联、商品 AI 变更集、内容审核状态、店铺发布版本等基础对象。

## 必须补齐的内容

| 优先级 | 必须能力 | 为什么必须 | Omnilink 现状与缺口 |
| --- | --- | --- | --- |
| P0 | 品牌事实、规则与版本 | 生成和审核需要能追溯当前使用的事实、语气与视觉规范，并知道规则是否通过校验。 | 有商家档案与 revision 等基础；首页没有展示品牌事实完整度、来源、规范检查和生效版本。 |
| P0 | 来源摄取与字段级证据 | 团队需要知道资料是否解析成功，AI 写入的商品事实来自哪里，以及失败后如何修复。 | `catalog_sources`、`catalog_item_sources` 和商品属性来源关系已有基础；首页没有摄取状态、失败原因或字段证据视图。 |
| P0 | AI 变更审核队列 | 对商品数据的 AI 修改必须可比较、可批准或拒绝，并记录操作者与结果。 | `catalog_item_change_sets` 已有审核生命周期；首页没有待审核总览和按字段展示差异、证据与置信度的队列。 |
| P0 | 渠道就绪检查与发布版本 | 发布前必须发现渠道必填项缺失，发布后能识别当前版本并回看或回退。 | `catalog_contents` 和 `storefront_versions` 支持内容审核与版本状态；首页没有统一就绪清单、发布状态、版本入口和回退流程。 |
| P1 | 商品可售状态 | “商品资料齐全”不等于“可卖”；变体、价格、库存和销售渠道需要分开判断。 | 商品管理已有相关对象；工作台未汇总各项缺失，也不该用检索向量推导价格或库存。 |
| P1 | 团队可追踪的任务与审计历史 | 本地对话历史不能支持跨设备协作、任务归属、审核记录或结果追溯。 | 工作台任务目前存浏览器 `localStorage`；应迁到持久化任务/产物，并关联商品、来源、Skill、模型和审核结果。 |

## 首页本次只补的部分

- 在原有 Hello 欢迎语和 AI 动态形象下方加入默认折叠的评测清单；展开后列出 4 项 P0 和 2 项 P1。
- 提供品牌资料、知识库、来源记录和商品库的现有入口。
- 明确这只是静态评测结果，不伪装成实时状态或待办数量。
- 未改动对话提交、composer、历史侧栏、欢迎动效和已有创作流程。

## 建议实施顺序

1. 做工作台汇总接口：品牌版本/校验、来源摄取、待审核变更、内容审核与发布版本。
2. 先落地 P0 审核与发布待办；每项需能跳到可执行的处理界面，不能只显示数字。
3. 给商品建立按渠道的销售就绪检查，将变体、价格、库存、素材和内容纳入规则。
4. 将本地任务记录迁为持久化工作流与审计事件，保留历史迁移或导出方案。

## 开源参考

- [BrandSpec](https://github.com/brandspec/brandspec)：将品牌规范作为结构化数据，提供 lint/评分与多格式 token 生成；对应品牌规则可验证、可版本化。
- [Brandcode System MCP](https://github.com/Brandcode-Studio/brandsystem-mcp)：强调品牌运行时、token 来源与置信度、合规检查和内容审核；对应来源治理和发布前校验。
- [brand-book](https://github.com/ordinarynerds/brand-book)：以结构化品牌资料支持文档与 token 输出；对应统一事实源，减少品牌文档漂移。
- [Medusa](https://github.com/medusajs/medusa)：将商品、变体、库存和销售渠道作为独立关联的商务概念；对应商品可售检查不能只看商品主记录。
